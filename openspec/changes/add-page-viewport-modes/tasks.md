## 1. Pure parameters

- [x] 1.1 In `extension/background.js`, add a named top-level `viewportModeParams(mode, tabWidth, tabHeight, uaMajor)`. It returns `null` for `fit` or an unknown mode. For a device mode it returns `{ metrics, touch, emitTouch, userAgent }`, following design.md Decisions 1–5. Inputs are coerced to finite positive numbers. - [x] 2.9 Fix live-reported regression: closing the side panel with a device mode active left the tab emulated at the old mode's layout (Chrome's grey PC-width margin still showing) even though the panel's own state already read Vừa khung. Root cause: closing the panel widens the tab at the exact moment its `"browzy-viewport"` port disconnects, and the old `clearViewportMode` awaited `ensureAttached`/the four clear commands BEFORE dropping `viewportModeByTab`'s entry — so during that await window the 500 ms `viewportPollTick` could see the size change, find the entry still present (2.7/2.8's post-await guard passed because the entry genuinely hadn't been dropped yet), and call `applyViewportMode` again with nothing serialising its CDP commands against the clear's. Fixed by serialising every apply/clear for one `tabId` through a per-tab promise chain (`viewportOpQueue` / `queueViewportOp`) so two operations on the same tab can never have `chrome.debugger.sendCommand` calls in flight at once, and by making `clearViewportMode` bump a per-tab generation counter (`viewportGenerationByTab` / `bumpViewportGeneration`) and drop the entry SYNCHRONOUSLY, the instant it is called, rather than after its CDP commands land. `applyViewportMode` now carries a generation through (a fresh one for an operator pick, the entry's own for `viewportPollTick`/`reapplyEmulatedTabsInWindow`'s automatic re-applies) and re-checks it immediately before every CDP command it is about to send, and once more right after they all land, undoing whatever it already sent and reporting itself superseded the instant it no longer matches. `onViewportDebuggerDetach` also bumps the generation for the same reason. Two follow-on correctness gaps found in self-review before being reported done: (a) a superseded operator pick used to resolve `{ok:false, reason:"superseded"}` straight back through `viewport_mode_set`'s `sendResponse`, which `sidepanel.js` (out of this change's scope) toasts as an error on any `!ok` — flashing a spurious error every time the operator changed their mind between two fast picks. Fixed with `viewportLatestResultByTab`: a superseded pick's response now chains to whatever superseded it (another pick, or a Fit) instead of reporting itself as failed, without risking a deadlock (its own queued CDP work still settles on the per-tab queue's own schedule, independent of this chaining layered on top). (b) the "undo" path on a superseded apply called `runViewportClearCommands`, which goes through `cdp()` → `ensureAttached()` — if the reason it was superseded was the debugger detaching (Cancel on the debugging bar) rather than a newer pick, this would silently RE-ATTACH the debugger the operator (or Chrome) had just detached, bringing the dismissed debugging bar right back. Fixed by only running the undo commands when `attachedTabs.has(tabId)` is still true, and reporting `"detached"` instead of `"superseded"` when it is not. A third gap found in a second self-review pass: the `viewportLatestResultByTab` chaining from (a) can itself self-reference — `onViewportDebuggerDetach` bumps the generation but (unlike every apply/clear) registered nothing as the tab's "latest", so a pick superseded specifically by a detach, then found re-attached again before it re-checks (any agent tool call on that tab attaches it), would see `attachedTabs` true again, report itself `"superseded"`, and find `viewportLatestResultByTab.get(tabId)` still pointing at its OWN wrapper promise — a promise chaining to itself never settles (V8 rejects it with "Chaining cycle detected"), silently breaking `.then(sendResponse)`. Fixed by (i) `onViewportDebuggerDetach` also registering `Promise.resolve({ok:false, reason:"detached"})` as the tab's latest result, and (ii) the wrapper refusing to chain to itself (`latest !== wrapped`) as a backstop. See design.md Decision 6's "Per-tab serialisation" bullet. ← (verify: `test/viewport-modes-wiring.test.mjs` — a poll-tick re-apply racing a panel-disconnect clear ends with the clear and no trailing `setDeviceMetricsOverride`; two rapid operator picks leave the final state matching the second pick with its commands landing uninterrupted and the superseded first pick resolving to the SAME outcome, not a bare failure; a bounds re-apply enqueued before a Fit pick is a no-op after the Fit; a device-mode pick superseded by an immediate Fit pick also chains to the Fit's own outcome; a debugger detach mid-flight reports `"detached"`, re-attaches nothing, and issues no further CDP command; a pick superseded by a detach then re-attached before it re-checks resolves — never rejects with a chaining cycle — to the detach's own outcome; each of these six was confirmed to FAIL against the pre-fix bodies before being restored)

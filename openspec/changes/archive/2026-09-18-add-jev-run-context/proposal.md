# Proposal: Jev Run Context (model-led steps, Jev element selection, verified completion)

## Why

A TypeSafe (Jev) run today is driven entirely by the decision model: it picks each step *and* judges completion itself, so a `DONE` is done-as-decided, the loop has no memory beyond `recent_actions`, and a stalled loop (no progress, the scroll brake, a repeated no-effect click) ends blocked with no second opinion. The architecture raised against this project — "LLM holds the memory/context; snapshots are sent to Jev; Jev takes action by selecting the right element" — corrected by the user's clarification that **everything except the click/element selection belongs to the configured model** — fixes exactly that split: the configured model (any capable, possibly vision-capable, OpenAI-compatible chat model) decides every step and holds the run's context, while Jev keeps only the thing it is fastest and best at: selecting the element for the step it is given.

## What Changes

- **Step decisions move to the configured model.** Each cycle, the profile's configured model — today used only for text values, navigation URLs, and the result report — decides the next step: the operation, a short plain-language intent naming the element, and any text value or navigation URL. The decision is validated strictly; a malformed answer (missing field, wrong type, oversize value, unknown operation, unrecognized key) ends the run with a named invalid-decision failure, and nothing dispatches from it. A well-formed step whose operation has no compatible element is recorded skipped with a target-unresolved reason and counts toward the no-progress bound instead of ending the run.
- **Element selection stays with Jev — its only decision.** For every target-bearing step the run makes exactly one strictly validated `POST /v1/systemone` carrying the goal, the memory, the observation, the step's intent, and a single target question for the decided operation. The operation question and the old speculative per-operation target fan-out are gone.
- **Run plan and memory.** The one-time goal-understanding note is replaced by a run memory (`plan`, `doneWhen`, `notes`) produced once after the first observation, carried in every request (step decisions, revisions, the check, recoveries, and the element-selection request), and revised through bounded advisory calls as the run progresses.
- **Verified completion.** A `DONE` step decision no longer ends the run on its own: one completion check gives the model the goal, the memory, and the final page, and requires a structured verdict. Confirmed → the run ends `done` with the report produced by the same check and the terminal record marked verified. Rejected → the step records the rejection, the returned guidance joins the memory, and the run continues; repeated rejection ends `blocked` with a `completion_unverified` reason. If the check itself is unreachable, the run falls back to today's done-as-decided outcome with the failure recorded on the terminal record (a **BREAKING** change for anyone reading run outcomes: `done` now distinguishes verified from unavailable).
- **Stall recovery.** Before the no-progress, scroll-brake, and repeated-no-effect-click guards end a run blocked, the model is consulted once for a way forward; if it returns guidance it joins the memory, the guards reset, and the loop continues (bounded per run). If it cannot help, or the recovery bound is spent, the run ends blocked with the same honest reason as today.
- **Removed**: Jev's operation question and its target fan-out; the separate text-value and navigation-URL calls (both fold into the step decision); the goal-understanding note and the result-summary call (replaced by the run plan and the completion check).
- **Visibility and copy.** A new durable `jev_memory` event records the plan, each update, and each recovery in the turn's row list; step rows read as the operation the configured model decided and the element Jev selected for it; the `DONE` step and the terminal record carry the verification; README and the settings hint for the text-model fields describe the broadened role; the TypeSafe settings disclosure names both call families.
- **Unchanged**: `anthropic`/`chatgpt` runs and their tool surface; `page_snapshot`; the dispatch discipline (run/lease/tab checks, protected-action backstop, approval cards, single-use grants, result-unknown handling); settings fields and ops; the capability test; the element-selection request's answer-validation rules; the bounds (60 actions / 120 step decisions).

## Capabilities

### New Capabilities
- (none — the change extends existing capabilities)

### Modified Capabilities
- `typesafe-jev-provider`: step decisions come from the configured model; the TypeSafe call narrows to one element-selection request per target-bearing step; the run's context is model-held (plan, bounded revisions, stall recovery); `DONE` becomes a verified completion check with honest fallbacks; the step record, terminal record, and reason vocabulary gain the new outcomes; a new durable `jev_memory` event joins the observable record.
- `browser-assistant-panel`: the "Jev run steps and outcome are visible" requirement extends to memory rows, to steps reading as operation-from-the-model plus element-from-Jev, and to labelling completion as verified versus judgment-alone.
- `agent-settings`: the TypeSafe disclosure broadens from "structured decision requests / small text-generation requests" to structured element-selection requests to TypeSafe and, to the configured text-model endpoint, the run's plan, each step decision, context revisions, the completion check, stall-recovery consultations, and generated text values.

## Impact

- **Host**: `host/agent/jev/text-helper.js` (the `NEXT_STEP` step-decision instruction and validator; plan, revision, completion-check, stall-recovery instructions; `TARGET_SELECTION`; `TEXT_VALUE`/`NAVIGATION_URL` and their request entry points deleted), `host/agent/jev/runtime.js` (per-cycle step decision → element selection → gate → dispatch flow; bounds; reasons; stop-ordering at terminal paths), `host/agent/jev/questions.js` (single target-question request for the decided operation; memory + intent in `state`), `host/agent/protocol.js` (reshaped step record, event vocabulary and payload docs); `host/agent/companion.js` only if a signature/marker changes; `host/test/` (runtime, text-helper, questions, run-path suites) and the mock TypeSafe/text-model fixture.
- **Extension**: `extension/sidepanel/conversation-model.js` (`jev_memory`, the reshaped step fields, terminal fields), `extension/sidepanel/tool-labels.js` (labels for the new rows/reasons and the reshaped step copy), `extension/sidepanel/sidepanel.js` (outcome line), `extension/settings/settings.html` (text-model hint and disclosure), and their tests.
- **Docs/specs**: README (the "Run it on TypeSafe (Jev)" section and the side-panel status paragraph), the three capability deltas above.
- **External calls**: one step-decision completion per cycle and one element-selection request per target-bearing step, plus the bounded plan/revision/check/recovery calls — usage and billing stay on the user's own two configured services, disclosed at provider selection.

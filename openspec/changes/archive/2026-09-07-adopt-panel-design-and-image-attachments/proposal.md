## Why

Two related, user-requested changes to the browser-assistant-panel capability, specification only — no product code, tests, or UI in this request:

1. **Adopt the approved panel visual treatment.** A design pass (`Main.dc.html`, `Empty.dc.html`, `Approval.dc.html`, `canvas.json`, reviewed and accepted) reworks how the panel presents an already-completed run and an empty conversation. The action timeline collapses to one summary row ("Đã dùng Browzy · N thao tác · <thời lượng>") that expands on click instead of filling the transcript with one row per tool call; a completed answer about structured data (a tender notice, in the reference content) renders as a label/value grid plus a one-line source citation ("dauthau.asia · đọc lúc 16:49"); and the empty state's suggestion chips fill the composer instead of sending immediately. `openspec/specs/browser-assistant-panel/spec.md`'s "Truthful action timeline and screenshot previews" and "Polished visual design" requirements predate this treatment and must be updated to require it, while every existing accessibility guarantee (WCAG 2.1 AA, 320px width, keyboard reachability, the polite live region) continues to hold — this is a presentation change, not a reduction in what the panel must remain usable by.

2. **Add image attachments to the composer**, with three entry points: drag-and-drop onto the panel, Ctrl+V paste from the clipboard, and a Ctrl+U keyboard shortcut that opens a picker modal for choosing image files. Scope is deliberately narrow this round: **images only**. General file/document attachment (PDFs, text files, anything Claude.ai's own composer accepts beyond images) is an explicit non-goal, not an oversight — the picker's contract is written so it does not foreclose adding that later.

The image-attachment half surfaces a real architectural gap, not a UI-only addition. `host/tool-definitions.js`'s existing `upload_image` (`host/tool-definitions.js:582-608`) and `file_upload` (`host/tool-definitions.js:622-642`) tools exist to let the **agent** attach a file to a **webpage's** `<input type="file">` during browser automation — `file_upload` is authorized against `RunUploadAllowlist`, an absolute-filesystem-path allowlist (`host/agent/policy/authorization.js:54-64,111-122`). A pasted or dropped image is a completely different thing: bytes the **user** hands to the **composer** so the **model** can see them as part of the message the user is sending — it never has a filesystem path (`DataTransfer`/clipboard `File` objects in a Chrome extension page do not expose one), so the path-based allowlist categorically cannot authorize it, and none of the existing machinery gets image bytes into the model's own turn at all. This change specifies the channel that carries those bytes from the panel to the model, reusing this project's own established pattern for exactly this problem — the bounded chunked native-messaging transport and artifact store already built for screenshot thumbnails (`host/agent/broker/chunked-transport.js`, `host/agent/companion.js:428-512`) — rather than inventing a new one. See `design.md` for the full analysis and the decision.

## What Changes

- Restyle the panel's completed-run and empty-conversation screens to the approved treatment: a collapsed-by-default action-timeline summary row that expands to a thin vertical guide with outline icons, natural-language labels, and screenshot thumbnails; a label/value grid plus a one-line source/capture-time citation for structured-fact answers; and confirmation that empty-state suggestion chips continue to fill the composer rather than auto-sending (already true in `extension/sidepanel/sidepanel.js:556-565` — restyled, not behaviorally changed). Every color in the approved mockup maps to an existing `extension/ui/tokens.css` dark-theme token with one exception (a muted tertiary/meta text tone, `#6b6459`, used for step metadata and inactive icon strokes, that has no defined token today); the light-theme equivalent is derived from the token system's light palette applying the same layout, not a literal copy of the dark mockup's hex values.
- Add a busy/working indicator — a solid terracotta starburst glyph (a new `spark` entry in `extension/ui/icons.js`, the shared icon module) beside a localized "Đang xử lý…" label — shown while a run's phase is queued or streaming with no answer text currently arriving for the current turn, including a gap of tool activity between answer segments, removed in place the instant answer text resumes, and never shown during waiting-for-permission, a pending ask-the-user question, stopping, stopped, interrupted, completed, or error. This is a deliberate, narrowly-scoped amendment to the panel's standing "no looping decorative animations" rule (`openspec/changes/archive/2026-09-06-migrate-to-claude-agent-sdk/design.md:111`): the glyph rotates and the label shows a slow brightness sweep only while a run is genuinely busy, both stop immediately (not at the end of their current cycle) the instant it isn't, and both are stripped under reduced motion to a static, still-legible presence per this capability's existing reduced-motion carve-out (`archived design.md:123-129`). The amendment covers this one glyph and this one label only; the standing ban on looping decorative animation stays in force everywhere else in the panel. See `design.md` Decision 6 for the full argument.
- Add an images-only composer attachment: drag-and-drop onto the panel, Ctrl+V clipboard paste, and a Ctrl+U keyboard shortcut opening a keyboard-accessible picker modal restricted to image files. All three entry points produce the same attachment representation — a thumbnail with a remove control, bound to the exact message it was attached to when Send is pressed, exactly like the existing page-context binding's "each submitted message SHALL retain its exact page-context identity" pattern (`openspec/specs/browser-assistant-panel/spec.md:27`).
- Accept `image/png`, `image/jpeg`, `image/webp`, `image/gif` — the exact set the pinned Agent SDK's own content-block type declares (`host/node_modules/@anthropic-ai/claude-agent-sdk/sdk-tools.d.ts:255,348`) — and reject every other drop, paste, or picker selection with a clear, specific reason shown to the user; this is the visible edge of the images-only boundary, not a silent ignore.
- Define a per-image and a per-message combined size ceiling (10 MB per image; up to 4 images, 20 MB combined, per message). These are this spec's own product decision, not a verified external API ceiling — the project supports arbitrary Anthropic-compatible gateways (`openspec/specs/agent-settings/spec.md`), so no single number is universally correct, and the chunked transport itself imposes no total-size limit (`host/agent/broker/chunked-transport.js:23`, 700KB per chunk, unbounded chunk count). Scaled from this repo's own analogous precedent for a single upload operation (`host/tool-definitions.js:624`, "Keep the combined size of all files in a single call under ~10 MB").
- Specify the bytes-vs-path transport: extension-side, attached image bytes are held in memory (mirroring the existing `screenshotStore` pattern, `extension/background.js:429`) and, on Send, chunked to the companion over the same bounded native-messaging transport already proven for screenshot artifacts (`host/agent/broker/chunked-transport.js`, `host/agent/companion.js:459-512`), tagged with a new attachment kind distinct from `action_artifact` so it is never confused with agent-captured screenshots or their retention/export rules. The companion resolves each attachment reference to its stored bytes and constructs the model turn as a multi-content-block `SDKUserMessage` (text plus one or more `{type:"image", source:{type:"base64", ...}}` blocks) — the exact shape this codebase already uses for its own vision capability check (`host/agent/settings/capability-test.js:298-312`, `host/node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts:5365-5414,2954`) — instead of the current plain-string `prompt` (`host/agent/companion.js:985-990`). This is additive to the existing versioned protocol (`host/agent/protocol.js`); no existing envelope shape changes, and an old companion that does not recognize a new message type already fails closed with an explicit `unknown_message_type` error (`host/agent/companion.js:198-202`) rather than silently mishandling it.
- Image bytes are never written to `chrome.storage`, extension logs, diagnostics, or settings/session exports — they exist only as in-memory panel state until Send, and on disk only under the same private, per-conversation, user-owned artifact directory already used for screenshot artifacts (`host/agent/storage/paths.js:31-32`), governed by the same existing secret/diagnostic-redaction guarantees the project already holds for that directory.
- An attachment is data the user supplied, never authorization: it cannot widen tab scope, tool permissions, or the `RunUploadAllowlist` upload allowlist, and it cannot itself satisfy a send/submit-class approval decision — exactly the same non-authority guarantee the existing ask-the-user answer already carries (`openspec/specs/browser-assistant-panel/spec.md:150-152`).
- The transcript shows what was actually attached and actually sent — never implying an image reached the model when storage, chunking, or send failed partway.

## Capabilities

### Modified Capabilities

- `browser-assistant-panel`: adopts the approved visual treatment for the action timeline and structured answers (restyling existing requirements) and adds images-only composer attachments across drag-and-drop, paste, and a Ctrl+U picker modal (new requirements).

## Impact

- Existing areas this change's implementation will touch (none touched by this spec-only request): `extension/sidepanel/*` (composer, panel-controller, protocol-client, sidepanel.css), `extension/ui/tokens.css` (one new token or a documented reuse decision for the muted tertiary tone), `extension/background.js` (screenshot-store-like in-memory attachment store, chunk transport sender), `host/agent/protocol.js` (new additive message type(s)/chunk kind), `host/agent/companion.js` (chunk ingestion for the new kind, multi-content-block prompt construction), `host/agent/storage/` (attachment artifact storage under the existing conversation artifact directory).
- No existing requirement in `openspec/specs/` is weakened. `browser-assistant-panel`'s accessibility, truthful-timeline, and page-context-binding requirements are restated as continuing to hold, not silently dropped, under the new visual treatment.
- No product code, dependency changes, installed browser settings, credentials, or live website actions are part of this spec-only change.

Reusing that same mechanism for a second, distinctly-tagged artifact kind is the smallest, most consistent answer — see Decision 1.

Today's actual run path only ever calls `query({ prompt, options })` with `prompt` as the plain string typed by the user (`host/agent/companion.js:777-990`, `_handleStart` → `_runAfterLeaseGranted` → `_runQuery`) — attachments require that path to branch to the multi-content-block form when attachments are present, and keep the existing plain-string form otherwise (no behavior change for the no-attachment case).
- **Accepted image types are the SDK's own declared set, not an invented list.** `host/node_modules/@anthropic-ai/claude-agent-sdk/sdk-tools.d.ts:255,348` declares `type: "image/jpeg" | "image/png" | "image/gif" | "image/webp"` for its own image content shape — this proposal accepts exactly that set.

Attachments are genuine multimodal *user message content* and cannot go through that channel; they must join the `prompt`'s own content array instead. Conflating the two would either silently drop the image (if stuffed into system-prompt text) or misrepresent user-supplied bytes as trusted page-context metadata — both violate the panel's existing "User messages and page/tool content remain distinctly typed" principle (archived design.md section 5).

This proposal's wire additions therefore stay under `PROTOCOL_VERSION = 1` (`protocol.js:19`) — new message type(s)/chunk `kind` values, and a new optional field on `START`, never a change to an existing required field's shape.

## Goals / Non-Goals

**Goals:** ship the approved dark-theme-derived visual treatment (collapsed timeline summary, structured answer + source line, chip-fills-composer) across both themes at all required widths without weakening any existing accessibility/truthfulness requirement; add images-only composer attachment across drag-and-drop, paste, and a Ctrl+U picker; specify a concrete, implementable answer to how attachment bytes reach the model, grounded in mechanisms this codebase already has proven (chunked transport, multi-content-block SDKUserMessage); keep an attachment strictly data, never authorization.

**Non-goals:** general file/document attachment (PDF, text, office documents, anything beyond the four accepted image MIME types) — an explicit, deliberate scope boundary for this round, not an oversight; changing the send/submit approval gate or ask-the-user tool; changing how bound page context is captured or rendered; a redesign of settings, history, or the skill picker; implementing the visual mockup's exact literal copy/labels verbatim (Vietnamese microcopy is illustrative, not a frozen string contract); resizing/recompressing attached images beyond the stated size ceiling (no client-side image transcoding pipeline is specified here); voice/audio attachment; attaching an already-captured screenshot from the action timeline as a composer attachment (a plausible future extension of the same mechanism, out of scope here).

## Decisions

### 1. Attachment bytes travel over the existing chunked transport, tagged with a new artifact kind

Reuse `host/agent/broker/chunked-transport.js` and the companion's existing chunk-ingestion path (`companion.js:459-512`, `_handleChunkEnvelope`) exactly as already proven for screenshot artifacts, with one addition: a second recognized `kind` value (distinct from `"action_artifact"`, e.g. `"user_attachment"`) so an attachment can never be confused with an agent-captured screenshot for retention, export, or timeline-preview purposes. Today's `_handleChunkEnvelope` already has the right shape for this — it stores based on `entry.kind`, and any kind other than `"action_artifact"` currently replies `stored:false, reason:"unsupported_kind"` (`companion.js:493-495`) rather than crashing or silently dropping bytes; recognizing the new kind is an additive branch alongside that existing one, not a rewrite of it.

Flow:

1. The panel captures image bytes from a drop, paste, or picker selection as an in-memory `File`/`Blob`, assigns a local attachment id, and holds it in an in-memory store scoped to the panel session (the same shape as `extension/background.js`'s existing `screenshotStore: Map<imageId, base64>`, `extension/background.js:429`) — never written to `chrome.storage`.
2. On Send, for each attachment still present on the composer at that instant, the extension chunks its bytes over native messaging using the same `chunk_begin`/`chunk_part`/`chunk_end` sequence `sendActionArtifactToCompanion` already uses for screenshots (`extension/background.js:1229-1259`), tagged `kind: "user_attachment"`, `conversationId`, `artifactId`, `mimeType`.
3. The companion acknowledges storage (mirroring the existing `ACTION_ARTIFACT_STORED` ack, `protocol.js:117-124`) before the message is considered sent with that attachment; a chunk sequence that fails validation (expired, size-bound violation, mismatched total — all already enforced by `ChunkReassembler`, `chunked-transport.js:96-160`) or an ack reporting `stored:false` must not let the panel proceed as though the image reached the model.
4. The companion resolves each attachment reference from the artifact store (the same per-conversation `artifacts/` directory already established, `host/agent/storage/paths.js:31-32`, in a subpath distinct from action-timeline artifacts) and reads its bytes only at the moment it builds that run's `SDKUserMessage` content — never re-transmitted, never cached in a second location.

Rejected alternative: embedding the base64 image directly inside the `START` envelope's `prompt`/`attachments` field. Rejected because it reintroduces exactly the problem the chunked transport was built to solve — Chrome's native-messaging message-size ceiling (`chunked-transport.js:4-11`'s own citation of the ~1MB historical limit) — for what could be several megabytes of image data in one message; the existing chunk transport already handles arbitrary total size via bounded 700KB chunks (`chunked-transport.js:23`) and has already been proven end-to-end for binary artifacts on this exact wire.

### 2. The model turn becomes a multi-content-block `SDKUserMessage` only when attachments are present

`_runAfterLeaseGranted`/`_runQuery` (`companion.js:889-990`) branch on whether the run has resolved attachments: with none, `prompt` remains the existing plain string, unchanged (`companion.js:982,985-990` today); with one or more, `prompt` becomes an async generator yielding exactly one `SDKUserMessage` whose `message.content` is an array of `{type:"text", text: <the user's literal composer text>}` followed by one `{type:"image", source:{type:"base64", media_type, data}}` block per attachment, in the order the user attached them — the same shape `capability-test.js:298-312` already constructs and the pinned SDK's own type declares (`sdk.d.ts:5365-5414`). The user's own literal text is never altered to mention the attachment (no synthetic "see attached image" text is injected) — the model sees the real text plus the real image blocks, exactly matching what the user actually sent, per the transcript-truthfulness requirement below.

Slash-command extraction (`extractSlashCommand`, `companion.js:78-...`) and bound-page-context rendering (`renderPageContextSystemPrompt`) already operate on the plain-text prompt and the separate `context` field respectively — neither needs to change; slash-command detection continues to read the user's literal text field before it is wrapped into content blocks.

### 3. Accepted types, size limits, and rejection

Accept exactly `image/png`, `image/jpeg`, `image/webp`, `image/gif` (`sdk-tools.d.ts:255,348`). Reject, with a specific reason shown in the composer (not a silent no-op):

- any non-image MIME type or a file with no readable image type (covers the entire general-file non-goal: a dropped PDF, a pasted text snippet as a file, a `.heic`/`.svg`/`.bmp`/`.tiff` image the accepted set excludes),
- a single image over the per-image ceiling,
- a selection that would put the message's combined attached-image bytes over the per-message ceiling.

Ceilings (this spec's own decision, not a verified external API ceiling — see proposal.md's "What Changes" for why no single number is universally correct across arbitrary Anthropic-compatible gateways): **10 MB per image; up to 4 images and 20 MB combined per message.** Flagged as an assumption: implementation must validate these against the actual configured gateway's real accepted request size during the existing connection-test flow (`agent-settings`'s "Explicit compatibility and connection testing" requirement) and adjust if a specific gateway's documented ceiling is lower; this is exactly the kind of gateway-variance risk `agent-settings`'s own spec already anticipates for tool/vision capability, not a new category of risk this proposal introduces.

### 4. Ctrl+U opens a picker; no artboard was supplied for it

None of the three provided artboards show the picker modal. This design specifies its required *behavior* — keyboard-triggered (Ctrl+U while the panel has focus, mirroring the existing composer keydown-handling location, `extension/sidepanel/sidepanel.js:734`), restricted to the four accepted image types, keyboard-accessible (reachable, closeable with Escape, returns focus to the composer on close), and visually consistent with the same token system and card/button treatment the approval and empty-state screens already establish — without inventing a specific unreviewed layout. **Risk, explicitly flagged:** Ctrl+U is Chrome's built-in "View Page Source" shortcut for ordinary tab content; whether Chrome allows an extension side-panel document to intercept it (side panels are not top-level tab content, but this has not been verified against real Chrome behavior) is an unverified assumption that must be checked early in implementation — if Chrome reserves it even inside the side panel, the requirement below still holds (a keyboard shortcut must open the picker) but the exact key combination is an implementation contingency, not a spec-level fact this document can verify without a live browser.

### 5. Attachment is data, never authority; truthful storage and transcript

Structurally identical to two guarantees this project already enforces elsewhere: page content is task data, never authorization (`openspec/specs/agent-browser-runtime/spec.md:35`), and an ask-the-user answer is data, never a permission (`openspec/specs/browser-assistant-panel/spec.md:150-152`). An attachment cannot widen `tabScope`, cannot add to `RunUploadAllowlist`, cannot itself satisfy a pending send/submit approval, and is never consulted by `authorizeToolCall` (`host/agent/policy/authorization.js:81-135`) for anything beyond confirming the referenced artifact belongs to this conversation. Bytes exist only in the panel's in-memory attachment store (pre-send) and the same private per-conversation artifact directory screenshots already use (post-send) — never `chrome.storage`, never a log line, never a settings/session export. The transcript records exactly which attachments were bound to a sent message and, if an attachment failed to store or chunk before Send, the run must report that failure explicitly rather than sending the text alone while the transcript implies an image went with it.

### 6. Busy/working indicator: a narrow, explicit amendment to the no-looping-animation rule, not a silent override

**The rule being amended, quoted exactly.** The archived migration's design.md — now this capability's standing visual rationale — states at section 5a: "Use 120–180ms opacity/color transitions; no looping decorative animations" (`openspec/changes/archive/2026-09-06-migrate-to-claude-agent-sdk/design.md:111`), and at section 5c, for the visible agent-pointer overlay: "Reduced motion removes decorative pulses/trails while preserving accurate position and dispatch state" (`archived design.md:123-129`). A rotating glyph plus a looping text shimmer is, read literally, exactly what the first sentence forbids. This decision does not pretend otherwise, and it does not quietly drop the user's request for a Claude-in-Chrome-style busy indicator either — it specifies the amendment explicitly, with a justification and a stated boundary.

**Why this qualifies as functional feedback, not decoration.** Every other place motion appears in this panel accompanies content that is already changing on its own (streaming text, a newly drawn cursor path) — the animation reinforces a change the user can already see. The busy/working indicator is the opposite case: it is the *only* signal available during the interval before a run's first answer token, or during a tool-activity gap mid-run, when literally nothing else on screen is changing. A user's own reference screenshot for this request shows an 18-second wait with no other visible activity; without a live signal, that reads as a frozen panel, not a working one. That is the functional case for an exception — distinguishing "the system is alive and working" from "the system is stuck" is exactly the kind of state truthfulness this capability's other requirements (the action timeline, the pointer overlay, the approval card) already exist to preserve, just applied to the one interval where no other content is available to carry that signal.

**Scope of the amendment — stated limits, not an open door.** This amendment covers exactly two elements, in exactly one place: the busy glyph's rotation and the busy label's brightness sweep, while the busy/working indicator itself is on screen. It does not relax 5a for any other panel surface, and it does not relax 5c's own reduced-motion carve-out for the visible agent-pointer overlay (click rings, drag trails) — those remain governed by their existing rules, unchanged. Both animations stop immediately — not at the end of their current rotation or sweep cycle — the instant the indicator is removed (Requirement "Busy/working indicator glyph and motion" below). Under `prefers-reduced-motion`, both loops are removed entirely, consistent with 5c's existing reduced-motion language, while the indicator's substantive information (that a run is busy, and for how long) remains visible in a static form — motion is the only thing reduced motion strips; the fact of being busy is preserved, per this capability's own existing principle that reduced motion removes decorative pulses while preserving accurate state.

**Glyph: identity, size, color, and the filled-icon exception.** A new named icon, `spark`, is added to `extension/ui/icons.js`'s `PATHS` map (per the Context finding above, this requires no change to `iconMarkup()` itself). Concrete geometry, as one valid realization of "an asterisk-like radial burst with alternating long and short spokes" in the module's existing 24×24 viewBox convention — an 8-point star centered at (12,12), with four long points at radius 9.5 on the cardinal axes and four shorter points at radius 6 on the diagonals, each pair of adjacent outer points joined by a quadratic curve whose control point sits near the center (radius ~2.2) to give concave "waists" between spokes rather than straight mechanical edges:

```
M12,2.5 Q12.84,9.97 16.24,7.76 Q14.03,11.16 21.5,12 Q14.03,12.84 16.24,16.24
Q12.84,14.03 12,21.5 Q11.16,14.03 7.76,16.24 Q9.97,12.84 2.5,12
Q9.97,11.16 7.76,7.76 Q11.16,9.97 12,2.5 Z
```

This path is this design's own original construction from the stated parameters (8 points, alternating 9.5/6 radius, ~2.2 concave waist, 24×24 viewBox) — it was authored to match the request's textual description of the reference glyph, not traced pixel-for-pixel from the screenshot (no pixel-level access to that image was available to this document). Implementation may redraw the exact curve while preserving the stated parameters. The `<path>` carries an explicit `fill="currentColor" stroke="none"` override, per the existing dot-accent pattern (`icons.js:29,30,32,52`) — the module's shared wrapper stays `fill="none" stroke="currentColor"` for every other icon, unmodified. Rendered at 18 CSS pixels (`--icon-size-md`, `extension/ui/tokens.css`'s existing icon scale — no new size token), colored via `--color-accent-text` (not the raw `--color-accent` swatch, which fails AA text-scale contrast on the light canvas per the Context finding above). Called with no `title` argument, so it inherits the module's existing `aria-hidden="true" role="presentation"` default — genuinely decorative, since the state itself is already communicated once through the label text and the live region, not twice.

**Motion: two independent, capped loops with an explicit reason each timing choice isn't drawn from `--motion-duration`/`--motion-easing`.** `tokens.css`'s existing motion tokens (`--motion-duration: 150ms`, `--motion-easing: cubic-bezier(0.2, 0, 0, 1)`) are scoped, by their own comment, to "120-180ms opacity/color transitions only" — a one-shot decelerate curve for a state change, not a shape built for an infinite loop (reusing it per-cycle would produce a visible stutter at each loop boundary, since a decelerate-to-stop curve implies an end, not a seam). This amendment therefore specifies its own loop timing, deliberately outside that token pair:
  - Glyph rotation: continuous, `linear` timing, one full 360° turn per 3.2 seconds, infinite while shown.
  - Label shimmer: a brightness sweep travelling across the label text, `linear` timing, one full pass per 1.6 seconds, infinite while shown, between `--color-text-secondary` (base) and `--color-text` (peak) — both already-existing tokens in both themes (Context finding above), so no new color literal is introduced.
  These two durations, like Decision 3's size ceilings, are this design's own product choice, not measured from the reference screenshot (a static image cannot itself prove an exact animation duration) — flagged accordingly in Risks below.

**Why the shimmer is flagged as the harder part of this amendment.** A moving brightness sweep across text is conventionally implemented as an animated gradient/`background-position` (or an animated `mask-position`) technique — not literally an "opacity" or "color" transition in the narrow sense 5a's wording uses. This document does not stretch 5a's wording to cover it by reinterpretation; it names the technique plainly and treats it, together with the rotation, as the amendment's actual subject matter, bounded by the scope limits stated above.

**Elapsed-time source.** When shown, an elapsed-time count is sourced only from the wall-clock instant `conversation-model.js`'s `_turnFor()` first creates the current turn object (`turn.ts = Date.now()`, `conversation-model.js:187`) — the same recorded-timestamp discipline this change's own collapsed action-timeline summary already relies on for its own elapsed-duration figure (MODIFIED "Truthful action timeline" requirement, this same spec). It is never estimated, interpolated, or restarted by an intervening tool-activity gap within the same run; on reconnect, the same anchor timestamp is restored from the snapshot rather than reset to "now" (mirroring the existing reconnect-restores-pending-state pattern this capability already uses for approval cards and questions, "Pending decision restored on reconnect"). A 3-second reveal threshold (below which no elapsed count is shown at all) is this design's own choice, to avoid a flashing "0s"/"1s" on the common case of a fast round trip — not a fact traceable to the reference screenshot, which only demonstrates that a long-wait affordance matters, not a specific threshold.

## Risks / Trade-offs

- [Ctrl+U may be intercepted by Chrome itself even inside a side panel] -> flagged in Decision 4; implementation must verify against a real browser early and fall back to a documented alternate combination if reserved, without silently dropping the "keyboard-accessible picker" requirement itself.
- [The mockup's one tertiary color (`#6b6459`) has no token] -> two concrete resolution paths named in Context; either is acceptable, but the visual result (a distinguishable, quiet metadata tone) is required either way.
- [Per-image/per-message size ceilings are this spec's own choice, not a verified gateway limit] -> explicitly flagged in Decision 3, with the existing connection-test flow as the place to validate/adjust per configured gateway.
- [A new chunk `kind` and message type are additive, but an old companion still rejects them explicitly] -> intended and safe (`unknown_message_type`/`unsupported_kind`, both already-existing fail-closed paths), not a silent failure; still worth a companion-version check in the implementation task list so a stale companion produces an actionable "update required" message in the panel rather than a bare protocol error.
- [Multi-content-block prompts change `_runQuery`'s call shape for the first time since it shipped] -> mitigated by keeping the plain-string path completely unchanged when no attachment is present (the overwhelmingly common case), so this is additive risk confined to attachment-bearing runs only.
- [This proposal deliberately amends the standing "no looping decorative animations" rule (design 5a, `archived design.md:111`), rather than working within it] -> justified in Decision 6: the busy glyph's rotation and label's shimmer are the only signal available during an interval where nothing else on screen changes, distinct from every other panel surface where motion already accompanies visibly changing content. The amendment is scoped to exactly that one glyph and one label, in one location; stops immediately (not at cycle end) the instant the run leaves the busy condition; and is stripped entirely under `prefers-reduced-motion` per 5c's own existing carve-out (`archived design.md:123-129`), while the indicator's substantive state remains visible without motion. No other panel surface, including the visible-agent-pointer overlay's own click/drag feedback, gains new looping motion as a side effect of this change.
- [The label shimmer's moving-gradient/`background-position` technique is not literally "opacity/color transitions" in 5a's own wording] -> named explicitly rather than fit by reinterpretation (Decision 6); implementation must use the technique specified there, confirm it degrades to a static, readable label with no layout shift when reduced motion strips it, and must not reuse `--motion-duration`/`--motion-easing` for either loop, since those tokens are scoped to one-shot 120-180ms transitions and were not designed for an infinite cycle.
- [`icons.js`'s shared wrapper renders every icon `fill="none" stroke="currentColor"`; the new `spark` glyph is the first *fully*-filled icon in the set, not just a dot-sized accent override like the existing ones] -> confirmed already expressible via the same per-path override the module's `alertTriangle`/`info`/`circleDot`/`browser` dot accents already use (`icons.js:29,30,32,52`), with no change to `iconMarkup()` or any other icon — but flagged as an explicit, stated exception to the module's outline-icon convention (`icons.js:1-4`), not a silent contradiction of it.
- [The glyph's exact curve coordinates, the rotation/shimmer durations, and the 3-second elapsed-time reveal threshold are this design's own product choices, not pixel- or frame-traced from the user's reference screenshot] -> flagged consistent with how Decision 3's size ceilings are already flagged; a static screenshot can prove that a glyph, a sweeping label, and a long-wait affordance exist, but not an exact path, duration, or threshold — implementation may adjust these within Decision 6's stated parameters (spoke count/alternation, token-sourced colors, "stops immediately" behavior, reduced-motion removal) without requiring a spec change.

## Migration Plan

1. Keep this change in planning state. All implementation task checkboxes remain unchecked.
2. On a later implementation request: land the visual restyle first (lower risk, no protocol changes), verified against both themes at 320/400/480px per the existing "Polished visual design" acceptance process.
3. Implement the attachment transport (extension-side capture/chunking, companion-side ingest/store, multi-content-block prompt construction) behind the same acceptance discipline the original SDK migration used — actual end-to-end image delivery proven against a real configured gateway before this ships as default, not merely unit-tested.
4. Verify the Ctrl+U interception risk (Decision 4) against a real Chrome/Edge/Brave side panel before committing to that exact key combination in product copy.
5. No rollback concerns beyond the existing panel's: both halves are additive to the panel and the protocol: an implementation that ships only the visual restyle, or only the attachment feature, or neither, does not corrupt existing conversations or break external MCP clients (`openspec/specs/agent-browser-runtime/spec.md`'s "Supported external MCP control" requirement is untouched by this proposal).

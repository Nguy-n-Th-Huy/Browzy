## 5. Correction pass: real per-request correlation and error surfacing

Verification found the shipped 3.x implementation only half-satisfied the spec: an explicit reopen of an unknown conversation surfaced nothing (the `error` case only acted on the startup-restore flag, never on `reopenConversation()`'s own request), and the single `_restoringConversationId` flag could not distinguish a concurrent boot-restore RESUME from an explicit-reopen RESUME, so either could hijack the operator onto a conversation they never asked for or leave a phantom `HistoryStore` row. This section replaces the flag with real per-request tracking.

- [x] 5.1 In `extension/sidepanel/panel-controller.js`, replace the single `_restoringConversationId` field with `_pendingResumes`, an ordered array of every outstanding RESUME (`{ conversationId, isBootRestore }`).
- [x] 5.2 `reopenConversation(conversationId, { isBootRestore = false })` pushes its own pending entry immediately before calling `protocol.resumeConversation()` (no `await` between push and send, so queue order can never drift from wire send order) and removes it on a synchronous send failure.
- [x] 5.3 `restoreOrStartConversation()` calls `reopenConversation(id, { isBootRestore: true })` instead of setting a flag directly, so its pending entry is distinguishable from any concurrent explicit reopen's.
- [x] 5.4 `_onEnvelope`'s `snapshot` case resolves the matching pending entry by `conversationId` (`_resolvePendingResume`), not by comparing against a single flag.
- [x] 5.5 `_onEnvelope`'s `error` case routes every conversationId-less `unknown_conversation` reply through a new `_handleUnknownConversationError()`: it FIFO-shifts the oldest outstanding entry, surfaces `model.connectionError` on THAT conversation regardless of whether it is an explicit reopen or a startup restore (fixes the explicit-reopen-surfaces-nothing gap), and only runs the "forget the remembered id, start a new conversation" fallback for a startup-restore entry when BOTH no explicit reopen has happened since boot (`_explicitReopenSinceBoot`, set synchronously at the top of `reopenConversation()` — see 5.5b) AND that entry is still `currentConversationId` at the moment the reply arrives — never for an explicit reopen.
- [x] 5.5b Add `_explicitReopenSinceBoot` (a controller field, set true the instant any non-boot `reopenConversation()` call is made, before its own `await`). `currentConversationId` alone is unreliable here: `restoreOrStartConversation()` needs three awaits before its own RESUME goes out, an explicit reopen needs one, so the boot restore systematically tends to send LAST and would otherwise "win" `currentConversationId` back from an operator action that happened first in real time.
- [x] 5.5c `reopenConversation()` also guards its own `_setCurrentConversationId()` call with `!(isBootRestore && this._explicitReopenSinceBoot)`, not only the fallback in 5.5 — otherwise a startup restore that reaches its send after an explicit reopen still steals display focus purely by optimistic pre-send assignment, even when the explicit reopen's own resume goes on to succeed (caught empirically by the concurrent-valid-reopen test in 5.9).
- [x] 5.6 `restoreOrStartConversation()` gains `if (this.currentConversationId) return;` at its top, restoring the pre-change `boot()` guard that a conversation opened from history during boot's earlier awaits must not be silently overwritten.
- [x] 5.7 Add a new `_startNewConversationSafely()` helper (swallows a `ProtocolClient` throw) and route BOTH `restoreOrStartConversation()` call sites that start a new conversation (the `!restorable` branch and the resume-failure catch) through it, so the method's "cannot reject" contract is actually true rather than only covering the resume attempt.
- [x] 5.8 Update `design.md`'s "Correlate the unknown-conversation fallback with an explicit restoring flag" decision (superseded) and its "Send failure falls back through the same path" decision to describe the `_pendingResumes` design and the fully-non-rejecting contract; add a Risks/Trade-offs entry for the remaining last-write-wins limitation on `currentConversationId` itself.
- [x] 5.9 In `test/sidepanel-fake-companion.test.mjs`, add: an explicit reopen of an unknown conversation surfaces the error on that conversation's model with `currentConversationId` unchanged and no `new` sent; concurrent boot-restore + explicit reopen both unknown does not hijack the operator onto a new conversation neither asked for; concurrent boot-restore (unknown) + explicit reopen (valid) leaves the operator on the valid conversation with no phantom `HistoryStore` row and the remembered id reflecting what is showing; `restoreOrStartConversation()` does not reject when the port is dead, covering both the `!restorable` path and the failed-resume-then-failed-new path. Update the existing `panel._restoringConversationId === null` assertion in the stale-id case to the equivalent `_pendingResumes` check.
- [x] 5.10 Re-run every `test/sidepanel-*.test.mjs` file with `node` directly and confirm all pass.

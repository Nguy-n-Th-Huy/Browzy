## Context

See proposal.md — Why. The constraints that actually shape the approach:

- `PanelController` is deliberately DOM-free; `sidepanel.js` is the only file that touches `document`. Restore logic must therefore live in the controller so tests can drive it directly, not in `boot()`.
- The active conversation identity is assigned in four places today: the two adopt branches inside `_onEnvelope`'s `snapshot` case (the `_awaitingNewConversation` claim and the "nothing open yet" claim), `reopenConversation()`, and the clear inside `deleteConversationLocally()`. Any one of them left un-persisted produces a stale remembered identity.
- The companion answers an unresumable `resume` with an `error` envelope carrying `reason: "unknown_conversation"` and **no `conversationId`** (`host/agent/companion.js` `_handleResume`, which catches the throw from `host/agent/session/manager.js` `resumeConversation`). The panel's existing `error` handling only acts when `env.conversationId` is present, so today this envelope is dropped entirely and the operator is left on an empty conversation.
- `ProtocolClient.resumeConversation()` and `.newConversation()` have identical send semantics — both call `_send()` immediately and both throw `"ProtocolClient: not connected"` when the port is gone — and `_handleResume`/`_handleNew` sit behind the same `_requireHello()` gate on the host. Swapping the startup call from `new` to `resume` introduces no new handshake ordering assumption.
- `HistoryStore` writes are already best-effort: a persistence failure must never block using the panel.

## Goals / Non-Goals

**Goals:**

- One and only one place in `PanelController` assigns the active conversation, so the persisted identity cannot drift from the in-memory one.
- Restore is an explicit, awaitable, DOM-free controller operation that a test can call.
- Every way a restore can fail converges on the same recovery: a usable new conversation and a cleared memory.

**Non-Goals:**

- Restoring composer draft text, attachments, or bound page context. Only the conversation identity is remembered; the transcript comes back from the companion's own snapshot.
- Any protocol, companion, or transcript-format change. `resume` and its `unknown_conversation` reply already exist and are used as-is.
- Multi-window coordination. Chrome runs one side panel instance per window; two windows racing on the remembered identity converges on last-write-wins, which is acceptable for a "where was I" hint and is not worth a lock.
- Replacing the local conversation index with a host-authoritative list. That gap is already documented in `history-store.js`'s header and is out of scope here.

## Decisions

### Store the identity under its own key, not derived from the index

`HistoryStore` gets a second storage key holding just the last-active conversation id, read and written through the same injected storage and the same swallow-on-failure pattern as the existing index.

Alternative considered and rejected: derive it as `list()[0]`, the most-recently-updated entry. `_persistHistoryEntry()` bumps `updatedAt` on every `stream_event` and `token_batch` for **any** model the controller holds — including a conversation the operator is not currently looking at (a background run finishing after the operator switched away). Most-recently-updated is therefore not the same question as last-viewed, and answering the wrong question here silently switches the operator to a conversation they did not choose. An explicit key is also cheaper to read at startup than sorting the whole index.

Clearing is expressed as writing `null`, so "never had one" and "deliberately forgotten" read the same at startup, which is what the fallback wants.

### Funnel all active-conversation assignment through one setter

A single private setter assigns `currentConversationId` and persists it, and all four existing assignment sites call it. Persistence is fire-and-forget with a swallowed rejection, matching how `_persistHistoryEntry()` and `recordPrompt()` already treat history writes — the panel must stay usable when `chrome.storage.local` is unavailable.

Alternative considered and rejected: persist only from `boot()` or only from `reopenConversation()`. Both leave the identity stale in exactly the case that matters most: the operator presses "+", chats in the new conversation, and closes the panel. The setter is the only place that provably sees every transition.

### Restore is a controller method, not logic in `boot()`

`restoreOrStartConversation()` on `PanelController` reads the remembered id, validates it against the local index, and either resumes it or starts a new conversation. `boot()` calls it in place of the current `if (!panel.currentConversationId) startNewConversation()` block and is otherwise untouched — the resume's snapshot arrives through `onEnvelope` and triggers the existing `onUpdate` → `render()` path, exactly as a new conversation's snapshot does today.

Validating against the local index before sending is what keeps a locally deleted conversation from being resurrected: `deleteConversationLocally()` removes the entry, and an id that is absent from the index — or present but flagged `deletedLocally` — is treated as not restorable without a round trip.

`restoreOrStartConversation()` also guards itself with `if (this.currentConversationId) return;` before reading anything. `boot()` awaits `pageContext.start()` and `panel.init()` before calling it, and `sidepanel.js`'s history "open" handler (`reopenConversation()`) is wired independently of `bootPromise` — a real Chrome side panel renders the history list and accepts clicks well before its own `boot()` promise settles. An operator who reopens a conversation during either of those earlier awaits already has a deliberate, real conversation active; restoring or starting a new one on top of it would silently discard that choice. This is the same protection the pre-change `boot()` had via its own `if (!panel.currentConversationId)` check, reinstated here because `restoreOrStartConversation()` otherwise runs unconditionally.

### Correlate the unknown-conversation fallback per outstanding resume, not with a single restoring flag

**Superseded.** The original decision here was a single `_restoringConversationId` flag, on the reasoning that it both correlates the fallback and scopes it to startup restore only. That reasoning covered attribution for a startup restore in isolation, but not the case this decision's own risk section didn't yet name: an operator can call `reopenConversation()` (a second, independent RESUME) *while the startup restore's own RESUME is still outstanding*, because the history list's "open" handler is wired independently of `bootPromise`. A single flag has no way to represent two outstanding RESUMEs at once, and — because `unknown_conversation` carries no `conversationId` at all — cannot tell whose failure just arrived. In production this produced two proven failure modes: (1) if both RESUMEs turn out unknown, whichever error lands first fires the fallback unconditionally, silently moving the operator onto a brand-new conversation they never asked for while the second (possibly the explicit reopen's own) error is simply dropped; (2) if the startup restore is unknown but the explicit reopen is valid, the fallback still fires blindly, and the *new* conversation it creates can end up both not displayed AND persisted into `HistoryStore` as a phantom row, while the remembered last-active id gets nulled even though the operator is looking at the conversation they explicitly reopened.

The corrected design: `PanelController` keeps `_pendingResumes`, an array of every RESUME currently outstanding, oldest first — `{ conversationId, isBootRestore }`. `reopenConversation(conversationId, { isBootRestore })` pushes its own entry immediately before calling `protocol.resumeConversation()` (no `await` between push and send), and removes it on a synchronous send failure. A successful reply (`snapshot`, which DOES carry `conversationId`) resolves its entry by id, wherever in the queue it sits. An `unknown_conversation` error — which carries no id — is attributed to `_pendingResumes.shift()`, i.e. the oldest still-outstanding entry.

That FIFO shift relies on one ordering fact, stated here because the wire itself cannot prove it: `_handleResume()` in `host/agent/companion.js` performs no `await` of its own before building its reply, and the transport between panel and companion (a `chrome.runtime.Port` in production, an in-memory queue in the fake-companion test harness) is a single ordered channel. Two RESUME sends therefore always produce their replies in the same order the requests were sent, so "oldest still-outstanding" is always "the one this reply answers" — provided queue order never drifts from send order, which is exactly what pushing immediately before the send (not earlier, in whichever call happened to start first) guarantees even when two `reopenConversation()` calls race each other.

Once attributed, the entry's `isBootRestore` flag governs what happens next:

- **Explicit reopen (`isBootRestore: false`)**: the failure is written to `model.connectionError` on the entry's own conversation, reusing the same mechanism a conversation-scoped error already uses — no second error channel. Nothing else changes: no fallback, `currentConversationId` untouched, no `new` goes on the wire (spec "Explicit reopen of an unknown conversation is not swapped").
- **Startup restore (`isBootRestore: true`)**: the same `model.connectionError` assignment happens first (so a restore failure is visible even mid-race), and the "forget the remembered id, start a fresh conversation" fallback fires *only if BOTH* `!this._explicitReopenSinceBoot` and `this.currentConversationId === pending.conversationId` hold. A concurrent explicit reopen (or a second restore-vs-reopen race in either direction) may have already moved `currentConversationId` elsewhere, or simply have HAPPENED at all, by the time this reply lands; firing the fallback anyway is exactly the hijack described above. Skipping it when either guard fails is safe precisely because the failure was already recorded on that conversation's own model in the step above — nobody may be looking at it right now, but it is there if the operator navigates back.

Two guards, not one, because `currentConversationId` alone is not reliable enough: `restoreOrStartConversation()` needs three awaited steps (`getLastActive()`, `list()`, then `reopenConversation()`'s own `promptsFor()`) before its RESUME ever goes out, while an explicit reopen needs only one (`promptsFor()`). A boot restore racing a near-simultaneous explicit reopen therefore systematically tends to send LAST — and because `_setCurrentConversationId()` used to run unconditionally right before the send, the boot restore would then "win" `currentConversationId` back from the operator's own earlier click, making the `currentConversationId` comparison alone say the wrong thing about which request the operator actually asked for most recently. `_explicitReopenSinceBoot` closes that gap: it is set SYNCHRONOUSLY at the top of `reopenConversation()` the instant an explicit reopen is *called* (isBootRestore false), independent of how long that call's own send takes to reach the wire, so it correctly reflects operator intent even when the boot restore's slower path would otherwise let it "win" the `currentConversationId` race afterward. It never resets, but only ever matters for the single boot restore a controller instance ever issues, so that is not a leak — once that restore's `snapshot` or `error` has been handled once, nothing reads the flag again.

The flag governs TWO places, not just the fallback decision above. `reopenConversation()` itself now guards its own `_setCurrentConversationId()` call: `if (!(isBootRestore && this._explicitReopenSinceBoot)) this._setCurrentConversationId(conversationId);`. Without this, the display-focus bug described above (boot restore reaching its send last and stealing `currentConversationId`) reproduces even on a startup restore that goes on to fail harmlessly — and, worse, reproduces even when the operator's own explicit reopen SUCCEEDS: the boot restore's later, purely optimistic pre-send assignment would still overwrite `currentConversationId` onto itself, and nothing in the `snapshot` case's adoption logic (which only fires when `currentConversationId` was null or a NEW was awaited) would ever move it back to the operator's already-resumed conversation. The startup restore's own RESUME still goes out either way — its model and `HistoryStore` entry stay in sync, and its reply is still correctly attributed via `_pendingResumes` — only the side effect of becoming the DISPLAYED conversation is skipped once an explicit reopen has already claimed that role.

### Send failure falls back through the same path, and the whole method cannot reject

`restoreOrStartConversation()` wraps every path that can fail — the `!restorable` branch's own `startNewConversation()` call, and the resume-attempt catch's fallback call, not just the resume attempt itself — through a new `_startNewConversationSafely()` helper that swallows a `ProtocolClient` throw ("not connected") rather than letting it propagate. `boot()` awaits `restoreOrStartConversation()` with no catch, and `bootPromise` itself has no `.catch()` either, so ANY rejection from this method — not only from the resume send — would abort the rest of startup, including the first `render()`, and leave the panel permanently blank. The original decision only wrapped the resume attempt, which left both `startNewConversation()` call sites free to reject on a dead port; `_startNewConversationSafely()` closes that gap without weakening the "the panel is left usable" guarantee: with no active conversation, `currentPhase()` already renders CONNECTING/ERROR purely from handshake state, and the next user action retries through its own already-guarded path.

## Risks / Trade-offs

- **A conversation the companion still knows but that failed for a different reason (transient companion error) is not distinguished from a genuinely unknown one** → Only `unknown_conversation` triggers the fallback; every other error reason keeps flowing through the existing conversation-scoped error path unchanged. A transient failure therefore surfaces as an error, not as a silent new conversation.
- **Fallback starts a new conversation, which is itself a visible state change the operator did not ask for** → It is the same state the operator gets today in this situation, minus the dead end. The remembered id is cleared at the same time, so the panel does not retry a known-bad restore on every subsequent open.
- **Two side panels in two windows overwrite each other's remembered identity** → Last write wins; each window still restores *a* real conversation and the operator can reopen the other from the history list. A cross-window lock is not justified for a hint of this weight (see Non-Goals).
- **Two explicit reopens racing each other (the operator clicks one history row, then another, before the first RESUME's reply lands) can still have either one "win" `currentConversationId`, because nothing disambiguates which of two concurrent explicit RESUMEs was issued last** → `_explicitReopenSinceBoot` only distinguishes a startup restore from *any* explicit reopen — it is set once and never reset, so it has no way to also tell two explicit reopens apart from each other; whichever of the two reaches its `_setCurrentConversationId()` call last wins, same last-write-wins acceptance as the cross-window case above. This does not corrupt either conversation's own state: the `_pendingResumes` FIFO queue still attributes each reopen's `snapshot` or `unknown_conversation` reply to its own conversation regardless of send order, so only which one ends up DISPLAYED is racy, not which one's error or history is recorded. This is a pre-existing property of concurrent `reopenConversation()` calls, not something this fix introduces or could remove without a wire-level request id (out of scope, see Non-Goals).
- **Startup now depends on a storage read before the first wire request goes out** → The read is a single key from `chrome.storage.local`, already awaited elsewhere during `panel.init()`, and any failure resolves to "no remembered id", which is exactly today's behavior.

## Migration Plan

None required. No stored format changes and no protocol version bump: the new storage key is simply absent on first run after upgrade, which the restore path already handles as "start a new conversation" — the pre-change behavior. Rollback is reverting the three source files; the orphaned storage key is inert and ignored by the previous panel.

## Context

See proposal.md for motivation and the five capability specs for behavioral requirements. This document is a proposed architecture, not a claim that SDK integration has already been demonstrated.

Repository findings:

- `extension/manifest.json` has no `key` or `side_panel`. The action currently starts/stops recording, and options point to `recorder/options.html`.

- `host/tool-runtime.js` already exposes in-process `init`, `callTool`, `shutdown`, and recorder events. Current transport is a user-named Windows pipe or POSIX socket (`host/endpoint.js`), despite stale TCP wording in README/comments.
- `host/native-host.js` owns the browser bridge. `host/codemode/common.js` already calls the runtime directly, without spawning an upstream MCP server. Reuse that separation.
- The actual registry has 26 tools, despite the README's 21-tool claim. The authoritative preservation inventory is: tabs_context_mcp, tabs_create_mcp, debug_timings, tabs_close_mcp, navigate, computer, find, form_input, get_page_text, gif_creator, javascript_tool, read_console_messages, read_network_requests, read_page, resize_window, shortcuts_list, shortcuts_execute, switch_browser, update_plan, debug, get_config, set_config, set_tab_focus, upload_image, retranscribe_recording, and file_upload. Hybrid adds execute_code and recording workflow integration.
- Existing runtime tracks sent/unsent requests and warns against replaying an action after a lost response. This behavior must survive the migration.
- A live run against `https://dauthau.asia/` (a Vietnamese tender-notice listing/index page) on a borrowed tab reproduced, against the real code, a weak-extraction / tool-steering / classifier chain recorded in decision 9 below.

## Goals / Non-Goals

**Goals:** a Claude-in-Chrome-like extension without a Claude product account/login/subscription, standalone sidepanel, official Agent SDK orchestration, automatically configured internal MCP browser tools, stable native-messaging identity, editable Anthropic-compatible settings, and regression-tested browser behavior.

**Non-goals:** implementing during this request; embedding SDK in MV3; using Anthropic's proprietary Chrome extension; pixel-identical cloning or unsupported parity promises; routing non-Claude models through Agent SDK; a pure browser-only distribution; adding voice chat (narrated recording remains); porting the full benchmark or modifying `REAL/`, `benchmark/`, or `scratch/`; deleting legacy code or user configuration.

## Decisions

### 0. Product identity and accountless onboarding

The approved product name is **Browzy**. Use it for the extension display name, panel header, settings, notifications, onboarding, installation copy and future mockups. Replace the earlier concept image's Open Claude label when producing revised visuals; that historical image is not the final branding reference. Keep Claude Agent SDK named accurately as an underlying technology and keep reference comparisons descriptive, without implying official affiliation.

A branding change must not rotate the extension public key, change its stable ID, rename native-messaging host identifiers, change MCP server/tool identifiers or break existing client launch paths. Product-facing names and technical compatibility identifiers are separate. No live rename or image regeneration is performed by this spec update.

The target is the familiar in-browser assistant experience without requiring the user to own or log into a Claude product account. The screenshots describe desired interaction and visual polish; they do not authorize bypassing authentication, subscription checks or borrowing proprietary account sessions. This is an independent extension, using supported provider API credentials and its own browser executor.

Onboarding is: install extension and native companion once, enter Base URL/API key/model, verify compatibility, then open the browser and use the assistant. Do not show Claude sign-in, require a Claude subscription, depend on saved Claude Code OAuth state, or invoke the proprietary Chrome integration. Keep SDK authentication explicitly in API-key mode and test a clean user profile with no ambient Claude credentials. A runtime that redirects to product login fails acceptance. If a gateway is incompatible, report that compatibility error rather than substituting login or claiming every API key works.

Product parity means the specified user flows (polished panel, current-page analysis, tools with visible cursor and timeline, settings, sessions and skills), not an unsupported guarantee of every proprietary feature. Record remaining gaps against these flows before release. No runtime API test has been performed during spec creation.

### 1. SDK in a native companion; reuse the browser executor

Proposed flow:

```text
Sidepanel/settings -> extension service worker -> native messaging host
                                                    |
                                            session companion
                                                    |
                                              Claude Agent SDK -> configured Anthropic endpoint
                                                    |
                                        SDK custom browser tools
                                                    |
                                          in-process SDK MCP server
                                                    |
                                    validated tool adapter
                                                    |
                                  tool-runtime / isolated code worker
                                                    |
                                     native host -> extension CDP
```

`host/agent/` owns sessions, provider configuration, browser broker, policy, and artifact storage. `extension/sidepanel/` and `extension/settings/` own UI. Native host multiplexes versioned agent messages and browser-tool responses, launching at most one companion for the active bridge. A child supervisor handles clean shutdown. Reconnection reconstructs session display from disk but never auto-resumes interrupted browser actions.

Keep the existing single-active-browser behavior. A companion-wide lease serializes runs across conversations and legacy clients. Every request carries run ID, conversation ID, browser identity, tab scope, and unique request ID. Browser switching releases the lease, verifies the new host handshake, then reacquires context. If another installed browser owns the global bridge, the panel identifies it; no request silently lands in another profile. Distinguish browser instances with installation/profile connection IDs, not a model-provided display name.

Protocol covers hello/version, start/resume, stop, permission decision, settings mutation/test, model discovery, recorder events, and sequenced stream events. Unknown versions fail closed. Reopening the panel requests a snapshot plus events after its last sequence number. Batch token updates to avoid flooding native messaging. Chunk binary results below the native-messaging message limit; validate chunk sizes, IDs, totals, and expiry. Test large screenshots and recordings rather than assuming arbitrary JSON fits.

### 2. SDK-managed browser tools with no mandatory user MCP setup

The user's follow-up accepts internally configured MCP. Use official `tool()` and `createSdkMcpServer()` APIs, passed explicitly through query options, to expose the existing browser runtime within the companion. This replaces the former proposed Bash/CLI transport entirely. No browser command client, shell grammar, separate MCP daemon, user MCP JSON, or `claude mcp add` step is required. The SDK adapter supplies validated argument schemas and returns text/image/error blocks, preserving screenshots as actual image content. Do not enable proprietary official Chrome integration; retain this project's extension and API-key settings.

Configure exactly the application-owned browser server for every session. Do not inherit arbitrary user MCP servers, hooks, plugins, credentials, or Claude settings. Validate run state, arguments, browser lease, and tab scope inside each tool handler, even when SDK permission checks preapprove the tool. Bind approvals to concrete actions; never treat page or skill text as additional authorization. Expose only needed built-ins for approved skills and session resources; Bash, Write, arbitrary filesystem reads, and subagents remain disabled by default. The browser's execute_code still runs inside the existing isolated worker.

After one-time installer registration, extension startup calls native messaging, which starts the host and supervised companion automatically. Browser restart reestablishes the connection and rebuilds internal tool registration without user commands. Initialize connection and local catalogs without sending a paid model prompt. Show readiness when the panel opens; starting generation requires a user message or explicit connection test. Do not claim the browser can programmatically open its sidepanel without a required user gesture. If initialization exceeds 60 seconds, show a specific startup error and retry control. Do not resume interrupted browser actions automatically.

Before switching defaults, test startup on a fresh machine without Claude Code MCP settings, all tool schemas, a real image-recognition fixture, cancellation, reconnect, and provider compatibility. Pin SDK/runtime versions after these integration checks. Failure blocks rollout and preserves the legacy application; it does not justify silently substituting the Anthropic API SDK. Internal MCP is the selected supported SDK integration, not an unwanted fallback.

### 3. Stable identity is independent of SDK selection

Ship one public manifest key maintained by the project and derive the Chromium ID from its decoded public-key bytes using the documented extension identity algorithm (first 128 SHA-256 bits mapped to a–p). Verify the derived ID against the browser before registration is considered healthy. Do not generate a new key each installation/build. Keep signing private keys outside the repository.

Installer reads the key, validates it, derives exact allowed origins, and updates only this product's host registration for chosen browsers. Retain browser/OS-specific native-host locations. Add a native PowerShell installer so Windows users need not depend on Git Bash for registration; keep POSIX support. Installation is idempotent and backs up replaced product registrations for repair/rollback. A moved companion directory requires updating its registered path once; that is separate from extension-ID stability.

Legacy unkeyed builds can receive a one-time different ID, and their extension storage cannot simply be read by the new ID. Provide non-secret settings/metadata export before migration and import afterward; re-enter secrets. Host-side recordings retain their current locations. Diagnostics separate ID mismatch, wrong path, runtime unavailable, protocol mismatch, and disconnected browser. Never use wildcard origins or edit unrelated extensions' registrations. Store publication is not part of this task; a future store release must preserve or deliberately migrate the public identity.

### 4. Anthropic-compatible settings, explicit credentials, bounded tests

Persist versioned non-secret profile JSON atomically in a per-user application configuration directory. Profile fields: profile ID, normalized base URL, model entries `{id, label}`, default model ID, revision, and last capability-test result keyed by endpoint/model/credential revision. Model IDs are opaque case-sensitive identifiers. Trim surrounding whitespace; require nonempty IDs, unique IDs, and a default referencing one entry. Start with an empty model list and discovery/manual entry, never a guessed model such as the screenshot's label.

Base URL is an origin with optional gateway prefix; reject URL userinfo/query/fragment, normalize trailing slash, and treat a terminal `/v1` as the API-version suffix rather than doubling it. HTTPS is required except explicitly marked HTTP loopback development endpoints. Reject cross-origin redirects for authenticated requests. No browser content script may issue provider calls.

At run start snapshot the profile into SDK `model` and isolated `env` values `ANTHROPIC_BASE_URL` and `ANTHROPIC_API_KEY` (x-api-key semantics). Do not also inherit auth tokens, provider switches, or ambient credentials. Bearer-only gateways are out of initial scope; they must not be made to work by silently changing API-key semantics. Existing recorder OpenAI transcription settings remain separate.

Use Windows Credential Manager, macOS Keychain, or Linux Secret Service behind a secret-store interface. If unavailable, show a persistence error and offer explicit memory-only credentials. Never fall back to plaintext. The trusted extension settings page can hold a just-entered key transiently for native transport; clear it immediately after success. Key replacement invalidates compatibility status. Key deletion cancels associated runs and removes stored secrets.

Model discovery calls the endpoint's Anthropic models API with pagination. Unsupported discovery leaves manual models untouched. Connection testing runs a bounded SDK session using synthetic content only: streaming text, one harmless fixture tool round trip, then image recognition. It sends no real tab content. Allow up to 60 seconds for cold runtime startup followed by a 30-second provider-test deadline and a maximum of 3 turns; distinguish startup, auth, model, rate limit, timeout, TLS/network, protocol, tool, and vision failures. Persisting settings is allowed offline; running the assistant requires a successful current endpoint/model capability test. A fresh model selection can trigger an explicit test. UI explains the small billed request.

Provider/model changes apply only to a new conversation; credentials can be rotated for the same profile after the active run ends. Existing runs retain their snapshot except explicit key deletion, which cancels them. Do not send historic context to a newly selected endpoint without the user creating a new conversation.

### 5. Sidepanel, permissions, and recorder coexistence

Use Chrome's sidePanel API and feature detection. Chrome/Edge/Brave on Windows are the first acceptance matrix; unsupported browsers show an explicit sidepanel-unavailable message while the legacy path remains usable. Add manifest permission and default panel. Reassign toolbar click to panel opening; put recording controls in panel plus existing options, keeping microphone setup and recorded-session browsing.

The screenshot informs a dark right panel, a visible webpage, a bottom composer, and model control. It does not establish account entitlement, supported models, microphone chat, or permission to act on the procurement website. Test only synthetic browser fixtures unless a separate real-site action is authorized.

Sessions own local transcripts and artifact references. Deleting history removes only app-owned conversation data and SDK artifacts, after explicit confirmation; recorded demonstrations have separate retention. Redact credentials and avoid recording raw provider request bodies in diagnostics. User messages and page/tool content remain distinctly typed. Prompt instructions reinforce page-content distrust, while code enforces scope and permission decisions. Approval tokens bind exact action/target/run, expire on stop or scope change, and are never reusable by webpage content.

### 5a. Visual direction and review deliverables

Design the product as a quiet, polished reading-and-chat companion inspired by the supplied Claude in Chrome references. Use a warm off-white light canvas (#F7F5F2) and charcoal dark canvas (#191918), slightly raised neutral surfaces, muted terracotta accent (#C4785B), and theme-specific accessible text/border tokens. These are starting values: adjust foreground/accent contrast to meet the stated accessibility target. Avoid heavy gradients, glass effects, saturated dashboard colors, dense borders, or gratuitous decoration. Do not imply official Anthropic branding or reproduce a logo without supplied assets.

Define shared CSS tokens for color, spacing, type, radius, shadow and motion. Use a 4px spacing base with 12–16px panel gutters, 14–16px readable UI/body text and 1.5–1.65 body line height. Prefer a system sans stack with full Vietnamese support; headings can use a restrained reading-oriented serif where legible. Composer radius 16px, menus/cards 10–12px, consistent 16–20px outline icons, and at least 32px pointer targets (44px for primary touch targets). Keep header compact, conversation visually dominant, and the composer anchored at the bottom with clear focus treatment. The page-context chip sits immediately above input and never competes with the answer.

Render assistant Markdown with carefully spaced paragraphs, headings, lists, quotes, readable code blocks, contained table scrolling, and clickable source labels. Tool steps collapse into a quiet activity row with status rather than filling the conversation with raw technical logs. Empty state uses a short greeting and current-page suggestions such as "Tóm tắt bài viết" and "Phân tích nội dung" when context is readable. Settings use the same components and grouped fields. Slash picker opens above the composer, has a bounded scroll area, highlighted keyboard selection, and an inline or adjacent description that stays inside the panel bounds.

Use 120–180ms opacity/color transitions; no looping decorative animations. Preserve scroll position when reading older content; auto-follow only when already near the bottom. Do not move the composer as tool rows expand. Support system theme with persisted light/dark override and reduced motion. Before implementation is accepted, produce polished screen mockups and then actual rendered screenshots for chat empty/streaming/long reply, skills, history, settings and error states at 320/400/480px in both themes. Review consistency, clipping, contrast and hierarchy against the reference; resolve all visible defects. A functional screenshot alone is not design approval. Keep visual artifacts under this change's review directory or a later explicitly scoped UI-artifact directory.

### 5b. Active-page binding and executor changes

On toolbar activation capture the triggering tab, window and browser connection; while an unpinned panel is open, track the active tab of that window. Never resolve from whichever unrelated window happens to be globally focused. Display local favicon/title/hostname immediately; do not read or transmit article bodies merely because the panel opened. At Send, atomically validate the displayed target, snapshot browser/window/tab ID plus URL/document identity and context revision, and bind them to the message/run. If UI and host revisions disagree, refresh the chip before dispatch instead of submitting against an invisible target. Offer pin/unpin and remove context; pin applies only while that tab/document remains valid.

For a request referring to the current article, provide the bound context as structured trusted metadata and call live page extraction (get_page_text/read_page as appropriate) before analysis. Use DOM/article content including content beyond the viewport when available, not only a screenshot or title. Track URL/route changes and document lifecycle, including SPA updates; invalidate stale element references on change. Extraction returns source URL/title, capture timestamp and completeness/truncation status. Tie citations/source labels to that capture. A changed/closed tab before capture yields an explicit stale-context result; never retry on a newly active tab. A navigation after a completed capture does not invalidate the historical source but must be visible if further reading is requested.

Current executor membership checks in extension/background.js and context instructions in host/tool-definitions.js assume managed tab groups. Adapt the SDK path to a validated per-run borrowed-tab scope. Do not simply disable membership checks or move the user's tab into the group. Bound article reading gets read-only access to that tab; mutations need authorization from the actual user task. Shared tool handlers must distinguish borrowed tabs from agent-created tabs so cleanup never closes or regroups borrowed tabs. Legacy MCP clients retain managed-group behavior. Revise SDK tool descriptions that currently mandate new tabs so they agree with current-page defaults; preserve all other executor behavior.

Test two windows, tab switches before/after Send, queued runs, pin/remove context, existing tabs outside the group, reload/redirect, same-URL document replacement, SPA article changes, restricted browser pages, login walls, long/truncated articles and tab closure. The primary acceptance fixture is: open article A, open extension, send the Vietnamese current-article request, and verify the answer uses unique facts present only in A with no URL prompt, new tab, navigation or unrelated-page read.

Emit start before execution, progress from actual dispatch, and completion/error only from executor results. Do not animate from a model's proposed plan or synthesize mouse activity for DOM/script calls.

Render an approximately 20px arrow with accessible contrasting outline and restrained terracotta accent; show a short click ring and held state for dragging. Default visible during control. Position the overlay using the same viewport coordinate system as dispatched input, accounting for frame offsets, scroll, browser zoom, device pixel ratio and sidepanel-driven viewport resize. Validate iframe and nested-scroll cases; never independently interpolate a different path or inject extra clicks to make the visualization look active. Reduced motion removes decorative pulses/trails while preserving accurate position and dispatch state. Throttle rendering without changing the action schedule. The sidepanel action timeline expands while a run executes and can collapse to a compact summary afterward. Use a thin vertical guide, consistent outline icons and natural labels such as Opened page, Finding link, Clicked, Waited 3 seconds, Captured page and Ran page script. Localize labels consistently. Successful dispatch is not proof of intended DOM effect; preserve existing post-action verification and unknown-outcome states. Screenshot thumbnails open a contained, keyboard-accessible image preview with timestamp/source and close control; do not fetch or recapture the current page when viewing history. Missing/deleted artifacts show unavailable, not a substitute image. The final answer stays separate from execution history. Validate visual and behavioral acceptance with click, double/right click, hover, drag, scroll, iframe coordinates, zoom/DPI changes, page navigation, active/background tabs, stop mid-action, lost heartbeat, failed/unknown results and screenshot overlay exclusion. Keep host/mcp-server.js, host/codemode/server-codemode.js and host/codemode/server-hybrid.js launch contracts working. Only sidepanel model sessions require the extension's provider profile. Existing recorder transcription still requires its own credential where applicable. The external client's model/auth is that client's responsibility. Sidepanel close or SDK failure must not shut down the shared host while the browser and external clients remain connected. Retain endpoint and parent-lifecycle compatibility tests.

### 8. User-decision gate for send/submit-class actions, and an application-owned ask-the-user tool

Product decision, authoritative and not to be widened: only sending/submitting-class actions wait for a user decision. Reading, extracting text, screenshots, scrolling, hovering, navigation clicks, typing into fields, filling forms, opening/closing agent-created tabs, and page script execution already within scope remain fully automatic — exactly what task 3.3's `tools`/`allowedTools` fix already auto-approves at the SDK layer (`reports/11-tool-permission-fix.md`). Submitting a form, clicking a send/submit/pay/confirm control, or a comparably hard-to-reverse outward-facing action instead suspends the run until the user answers a visible allow/deny card in the panel (the user's own words: a notice to "cấp quyền" — grant permission — like Claude in Chrome). This narrows, not widens, the existing "Actions outside the task's existing authorization SHALL wait for a user decision" requirement already in specs/browser-assistant-panel/spec.md's "Scope and permission controls".

**SDK mechanism — verified from `host/node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts` (pinned `0.3.263`), what is a product decision noted separately.** `Options.canUseTool` (sdk.d.ts:1454, type `CanUseTool` declared sdk.d.ts:209-269) is "Called before each tool execution to determine if it should be allowed" and must resolve `Promise<PermissionResult | null>`. Its own docstring is explicit that there is no park deadline of the SDK's own: "Return `null` ONLY after the consumer has already sent the control_response out-of-band... Fail-closed: an accidental null means no response is sent and the tool stays blocked indefinitely — permission prompts have no park deadline" (sdk.d.ts:203-208) — so the companion, not the SDK, must own the only timeout that exists (see "Timeout and abandonment" below). `PermissionResult` (sdk.d.ts:2339-2352) is `{behavior:'allow', updatedInput?, updatedPermissions?, toolUseID?, decisionClassification?}` or `{behavior:'deny', message, interrupt?, toolUseID?, decisionClassification?}`; `message` is mandatory on deny and `interrupt` is optional (falsy by default), which is the field this design relies on so a denied call ends only that tool call, not the whole run. `CanUseTool`'s second parameter always carries `toolName`, `input`, and a `requestId`/`toolUseID` (sdk.d.ts:209-262); it may also carry `title`/`displayName`/`description` "rendered by the bridge", but that docstring is written for the CLI's own built-in tools, and whether the bridge populates them for a call into this project's own in-process MCP tools is not stated anywhere in `sdk.d.ts` — treated here as an unverified, opportunistic enhancement only, never the sole source of the approval card's text. The card's actual text is built from this design's own classifier (below), not assumed from these fields.

It is likewise unverified from `sdk.d.ts` alone whether `canUseTool` is invoked at all for a tool name already present in `allowedTools`, or whether an `allowedTools` match short-circuits before the callback ever runs; `reports/11-tool-permission-fix.md`'s reproduction only proves the reverse case (a tool absent from `allowedTools`, with no `canUseTool` set, was denied). This design does not need that question resolved: the classification below is tool-name-scoped, not per-call, so the architecture is correct either way it turns out to behave — flagged here explicitly as an unverified assumption to check empirically at implementation time, per task 1's acceptance-gate discipline.

**`tools` vs `allowedTools`, restated and now load-bearing.** `tools` (sdk.d.ts:1497-1508, "Specify the base set of available built-in tools") is the base availability allowlist; `allowedTools` (sdk.d.ts:1442-1449, "List of tool names that are auto-allowed without prompting for permission... To restrict which tools are available, use the `tools` option instead") is the separate auto-approval allowlist task 3.3's fix already established, and the two must never be conflated (`reports/11` documents exactly this confusion causing the original regression). Because `allowedTools` operates at the granularity of a whole tool name, and this project's `computer` and `javascript_tool` tools can each produce both an always-automatic call (a non-submit click, typing, scrolling, an in-scope script) and a send/submit-class call (a click on a submit control, a script that submits a form) under the identical tool name, those two tool names alone must be removed from `allowedTools` — they remain in `tools` for availability — so every one of their calls reaches `canUseTool`, where the classifier decides per call. Every other browser tool (`navigate`, `form_input`, `tabs_create_mcp`/`tabs_close_mcp`, `upload_image`, `file_upload`, `gif_creator`, `shortcuts_execute`, `resize_window`, `set_tab_focus`, `set_config`, and every read-only tool) can never itself produce a send/submit-class call per the classification below, so it stays in `allowedTools` exactly as task 3.3 left it, with zero added latency and no dependency on `canUseTool` ever being invoked for it. The approval-gated actions must therefore never sit in `allowedTools` — this is the concrete, load-bearing consequence of the distinction above.

**Classification — reuses, does not replace, `host/agent/tools/mapping.js`.** `isMutatingCall()`'s existing mutating/read-only split stays exactly as-is and continues to govern the separate borrowed-tab-mutation question below. A new, narrower predicate sits only in front of the two tools named above and returns true only for: a `computer` click/key call whose resolved target (via `find`'s element metadata, or the DOM at dispatch time) is a submit-type control (`<button type="submit">`/`<input type="submit">`, a `<form>`'s implicit default-submit button, or an accessible name/role matching a documented, localized submit/send/pay/confirm keyword list — Vietnamese included, e.g. "gửi", "xác nhận", "thanh toán", "đặt hàng"); or a `javascript_tool` script whose text calls `.submit()` or dispatches a `submit` event on a form element (a best-effort static/runtime check; a script that submits a form through indirection the check cannot see is a disclosed residual risk carried forward to implementation, not a silently accepted gap, and such a call still passes through the unconditional handler-side checks below regardless). Every other click, hover, drag, type, key, scroll, wait, screenshot, zoom, and non-submitting script is not gated, matching "automatic, never prompts" exactly. This predicate — not "any mutation" — is the only thing `canUseTool` ever suspends.

**Approval tokens.** Reuses `host/agent/policy/approvals.js`'s existing `ApprovalRegistry` and `host/agent/session/run.js`'s existing `issueApproval()`/`consumeApproval()` unchanged. On a gated call, `canUseTool` calls `run.issueApproval(action, target)` — `action` is the exact tool name plus a normalized description of the send-class intent (e.g. "submit form", "click Pay"); `target` is the concrete `{tabId, ref}` or equivalent — to mint a token bound to that run/action/target, exactly as `ApprovalRegistry.issue()` already does. The token itself is never sent over the wire; only a `requestId` correlating the pending decision leaves the companion process. When the panel answers, the companion consumes the token via `run.consumeApproval(token, action, target)` (already implemented and already tested: `run_mismatch`/`action_mismatch`/`target_mismatch`/`already_used`/`expired`/`unknown_token` are all real, distinguishable rejections) before resolving `canUseTool`'s promise — so a token minted for one exact action/target/run can never authorize a different call, a different tab, or a later run, and nothing on a page or in a skill can hand itself a token, because nothing in this path ever reads a token from tool arguments, page content, or skill text. Stop already calls `approvals.invalidateForRun()` (`Run.stop()`, unchanged); a scope/browser change already calls `approvals.invalidateAll()`. This capability adds one more caller of that existing `invalidateAll()`: credential replacement or deletion for the active profile (decision 4's "Key replacement invalidates compatibility status. Key deletion cancels associated runs...") must also invalidate every outstanding approval, so a token minted under one credential can never be consumed after the credential backing that run has changed.

**Handler-side authorization stays unconditional.** This restates decision 2 verbatim, because it is exactly as load-bearing here: "Validate run state, arguments, browser lease, and tab scope inside each tool handler, even when SDK permission checks preapprove the tool." An `allow` `PermissionResult` from `canUseTool` only lets a call reach `host/agent/tools/adapter.js`'s `authorizeToolCall()` and `enforceBorrowedTabScope()`, which run exactly as they do today, unconditionally, on every dispatch. A user's "allow" answer authorizes exactly the one action/target the card described; it never widens tab scope, never lifts the borrowed-tab-mutation default for unrelated future calls, and never substitutes for those checks failing for an unrelated reason (e.g. the target tab having left the run's scope between request and decision).

**Borrowed-tab mutations, clarified rather than widened.** `host/agent/tools/mapping.js`'s `authorizeBorrowedTabMutation()`/`enforceBorrowedTabScope()` hook (decision 5b) is today dormant — nothing calls `authorizeBorrowedTabMutation()` (`reports/11`) — so any mutating call against a borrowed tab is currently rejected outright, regardless of this capability. That default cannot stand alongside "typing into fields, filling forms... automatic, never prompts": the user's own decision requires those to work on the bound page, and that page is normally a borrowed tab (decision 5b; specs/agent-browser-runtime/spec.md's "Live current-page reading" requirement). This capability resolves it, without widening the existing runtime requirement: the moment a run's own instruction legitimately calls for interacting with its bound tab, `authorizeBorrowedTabMutation(run, tabId)` is invoked automatically for that tab — mirroring how "Live current-page reading" already authorizes reading a borrowed tab without a confirmation — so the automatic action set (typing, filling, non-submit clicks, scrolling, hovering, in-scope scripts) runs with neither a prompt nor a dead-end rejection. **Corrected by decision 9d below, after live evidence:** `javascript_tool` is excluded from this automatic grant — only `computer`'s non-submit-classified actions and `form_input` are included, because `authorizeBorrowedTabMutation()` is a per-tab flag with no notion of which tool asked, and granting it for an unrelated reason would silently also authorize a later navigating script. This does not touch the existing runtime requirement that a mere read/analyze request does not by itself authorize "navigation, submission, closing, or regrouping" of that tab, and it does not touch the separate, absolute rule that agent-created-tab cleanup never closes or regroups a borrowed tab. The one gate that stays interactive — for a borrowed tab exactly as for an agent-created one — is the send/submit approval card; an "allow" answer authorizes only the named action, never a blanket future-mutation grant.

**Timeout and abandonment.** Because `canUseTool` has no park deadline of its own (quoted above), the companion enforces one explicitly: the issued approval's own TTL (`ApprovalRegistry`'s existing `defaultTtlMs`, 5 minutes) doubles as the wait budget. If no matching decision arrives before the token expires, `canUseTool` resolves `{behavior:'deny', message: <specific, user-legible timeout reason>}` — never `null`, never an indefinite hang. Deny does not itself stop the run (see the panel-spec scenario); the transcript records the action as denied-by-timeout, distinct from a user's explicit deny, so a later review is never misled about whether a human actually answered. The panel clears its own pending-approval state at the same moment rather than continuing to show an already-timed-out card as awaiting an answer. Stop, browser-scope change, or credential change occurring first invalidate the token exactly as above and resolve the same way — deny, with a reason identifying which of the three happened — rather than leaving the promise unsettled.

**The ask-the-user tool.** An application-owned SDK tool, registered the same way as the existing browser tools — via `tool()`/`createSdkMcpServer()` (the pattern `host/agent/tools/adapter.js` already uses for all 26 browser tools) — rather than the SDK's own built-in `AskUserQuestion` tool (input/output shapes documented at `sdk-tools.d.ts:1026` and `sdk-tools.d.ts:3665`; its per-query rendering hint is `Options.toolConfig.askUserQuestion.previewFormat`, sdk.d.ts:1561-1568). The built-in tool is deliberately not selected, for two verified, cited reasons rather than a guess: first, its host-rendering path is the generic `request_user_dialog`/`Options.onUserDialog` control-request channel (sdk.d.ts:1618-1644; `UserDialogRequest`/`UserDialogResult` declared at sdk.d.ts:8697-8721), gated by `Options.supportedDialogKinds` (sdk.d.ts:4018) — but the exact `dialogKind` string the built-in tool actually uses is not present anywhere in the pinned SDK's type definitions (only the unrelated example `'refusal_fallback_prompt'` is documented), so wiring it correctly cannot be verified at spec time; this is recorded here as an **explicit unverified assumption to check empirically at implementation time**, not silently assumed away. Second, the built-in tool's own idle/auto-continue behavior (`askUserQuestionTimeout`) is a field of the persisted `Settings` interface (sdk.d.ts, `Settings` starting at line 5748), not a per-`query()` `Options` field — and this project's isolated sessions already disable filesystem settings via `settingSources: []` (decision 2), so that knob would not even apply here. An application-owned custom tool sidesteps both open questions: its handler is ordinary application code with the same well-understood `CallToolResult` contract as every other registered tool, and the companion controls its own wait/timeout policy the same way as the approval gate above, using the same mechanism rather than a second, differently-behaved one.

Contract: the tool's input schema takes one question, a short header, and 2-4 pre-written answer options — `{question, header, options: [{label, description}], multiSelect?}` (mirroring the built-in tool's own well-designed shape at `sdk-tools.d.ts:1026`, without adopting its unverified wiring). Its handler emits a sequenced stream event (the same restorable mechanism as the approval request below) carrying the question, options, and a `requestId` to the panel; renders a question card; and awaits the user's chosen option(s) over a new wire message pair symmetric to the existing `approval_request`/`approval_decision` pair already declared in `host/agent/protocol.js`'s `AGENT_MESSAGE_TYPES` (e.g. `question_request`/`question_answer`). The handler resolves with the chosen option's label/value as plain tool-result content — the SDK sees an ordinary tool result, nothing more. This grants the run **no authority**: the answer is data the model can read and act on in its next turn, exactly like a `read_page` result; it is never treated as a `PermissionResult`, never consulted by `canUseTool`, and never substitutes for the approval card above — a model cannot phrase a question so that answering it also authorizes a send/submit-class action. The same timeout/abandonment discipline as approvals applies: an unanswered question times out with an explicit, distinguishable tool-result error rather than hanging the run, and a stopped run invalidates its own pending question exactly as it invalidates pending approvals.

**Reconnect.** A pending approval request and a pending question are both ordinary sequenced stream events (`TranscriptStore`; decision 1's "snapshot plus events after its last sequence number"), building on the wire shape `extension/sidepanel/conversation-model.js` already anticipates (`pendingApproval = {runId, action, target, requestId, ts}`, driving the existing `WAITING_FOR_PERMISSION` run phase). Reopening the panel replays them from the snapshot exactly as it replays any other event, so a pending decision survives a reconnect without duplication. Neither is ever auto-answered on reconnect or on any other implicit trigger — the run stays suspended, or the question stays outstanding, until an explicit `approval_decision`/`question_answer` arrives, or the timeout above fires.

### 9. Live evidence: extraction honesty, listing-page reading, and the javascript_tool borrowed-tab gate

A live run against `https://dauthau.asia/` — a Vietnamese tender-notice **listing/index** page, not an article — on a borrowed tab surfaced three linked defects. Recorded here because they were reproduced against the real code, not hypothesized, and because they chain into each other: fixing only the last one would not fix the problem.

**Borrowed-tab binding worked correctly, and nothing below may weaken it.** `get_page_text` succeeded on the bound tab, and the runtime surfaced to the model exactly the instruction decision 5b specifies: "This run's context already includes tab(s) [1300524375] as the current page(s) provided for it — read-only by default; mutating one needs explicit task authorization. Create a new tab with tabs_create_mcp only if the task genuinely needs a separate page."

**Extraction was inadequate, and reported success anyway.** `extension/content.js`'s `getPageText()` (lines 315-359) walks a fixed selector list — `article, main, [class*="articleBody"], [class*="post-content"], [class*="entry-content"], [role="main"], .content, #content` — and falls back to `document.body` only if none match. On this listing page one of the *specific* selectors matched a small `<div>`; the actual result was `Source: <div>` with `Complete: yes`, capturing only footer/contact boilerplate ("Thông tin liên hệ 0904.634.288, 024.8888.4288 contact@dauthau.asia Facebook Fanpage: ... Messenger: ...") — none of the tender listings that are the page's real content. `Complete:` (`extension/background.js:3010`) is derived from exactly one signal: `truncated = fullText.length > MAX_CHARS` (`content.js:342`), a length check against a 100000-character ceiling, with no signal for whether the matched container actually held the page's principal content. A short, wrong extraction and a long, correct one are indistinguishable to the caller: both can report `Complete: yes`. This directly contradicts the existing "SPA and incomplete extraction" scenario's "reports missing portions instead of claiming a complete reading or fabricating content" — not because that scenario's requirement is wrong, but because today's implementation has no mechanism to detect this failure mode at all.

**A read-only script was rejected as a mutation.** Having received boilerplate, the model called `javascript_tool` with a `querySelectorAll('a')` filter-and-slice script that mutates nothing, and it was rejected: `"Tab 1300524375 is a borrowed page tab bound to this run's context (read-only by default). Mutating it requires explicit authorization from the actual user task, which this call does not have." — Từ chối: borrowed_tab_mutation`. This is `host/agent/tools/mapping.js`'s `BorrowedTabMutationError` (lines 290-299), thrown by `enforceBorrowedTabScope()` (lines 312-328) because `isMutatingCall("javascript_tool", ...)` (line 250) is unconditional: `javascript_tool` sits wholly inside `MUTATING_LEGACY_TOOLS` (line 228), with no per-call distinction the way `computer` gets via `COMPUTER_READ_ONLY_ACTIONS` (line 243). A second call in the same run, `window.location.href='https://dauthau.asia/thongbao/moithau/'`, was **correctly** blocked by the identical gate — that one genuinely navigates the tab. Both calls hit the same code path for different reasons: one correctly, one not.

**Causal chain.** Weak extraction on a listing page → the model resorts to page scripting to enumerate content → page scripting is blocked by a coarse, tool-name-level mutation classifier. The blocked script is the last symptom, not the cause; fixing it in isolation — by loosening the classifier, or by prompting on every script — would be exactly the moves this design's constraints already rule out (below). The fix belongs upstream, in extraction quality and tool-choice steering.

**9a. Honest completeness reporting.** `Complete: yes` must mean the captured container actually held the page's principal content, not merely that its text was shorter than the truncation ceiling. Add a second, independent signal alongside `truncated`: a coverage check comparing the matched container's cleaned text length against the same page's `document.body` cleaned text length (`coverageRatio`), computed with the identical cleaning already applied to `fullText` (script/style/noscript/template/svg stripped, whitespace collapsed) — no new page-content classifier, no semantic judgment of *what* the missing content is, only how much text exists outside the captured container. A container that resolved through the fixed selector list yet holds an implausibly small share of the page's total text, while the page carries substantially more content outside it, is a low-confidence extraction. In that case the header MUST report a status distinct from `Complete: yes` — naming the container it used and stating that other page content was not captured (e.g. `Complete: partial (container <div> captured a small fraction of the page's text; try read_page or find for listing-style pages)`) — exactly matching the existing "report missing portions instead of claiming a complete reading" requirement rather than a new one: this is that requirement's missing detection mechanism, not a rival to it. `document.body` as the absolute fallback (no selector matched at all) is always reported this way regardless of the ratio, since there was no candidate content container in the first place. This is a page-content statistic (how much text exists where), not a judgment of arbitrary code behavior, so it does not run into the hard limit decision 9d relies on, which is specific to inferring intent from executable script text.

**9b. Listing/index pages already have a read-only path — the gap is that nothing points the model to it.** `read_page`'s accessibility tree (`content.js`'s `generateAccessibilityTree`, line 217) already emits `href="..."` for every anchor (line 271) and can be filtered to `interactive` elements only — this is exactly the "enumerable links with their text" the model tried to get by hand with `querySelectorAll('a')`. Its indentation reflects DOM nesting, so a listing's repeated item structure (row after row of the same shape) is visible in the output too. `find`'s natural-language query (up to 20 matches) is a second read-only path for a narrower ask (e.g. "tender notice links"). Neither tool needed to change to cover this evidence's need. The gap is that nothing steers the model there: `get_page_text`'s own description says it is "prioritizing article content" (`host/tool-definitions.js:237`) with no mention of what to use when there is no article, and `read_page`/`find`'s descriptions don't mention that they cover exactly this case. That is decision 9c's fix.

**9c. Tool-description steering — the cheapest fix, and it widens nothing.** Extend `host/agent/tools/mapping.js`'s existing `sdkFacingDescription()` (the same mechanism that already appends `LIVE_EXTRACTION_NOTE` to `get_page_text`/`read_page`, lines 101-118) with: (1) a note on `get_page_text` that a fallback container, or a short result on a page that looks like a listing/search/index (many similar repeated links, no single dominant text block), means `read_page` (filter `interactive`) or `find` should be tried instead of assuming the page has no more content; (2) a note on `read_page`/`find` that they are the read-only way to enumerate links/items on such pages; (3) a note on `javascript_tool` that it is reserved for cases genuinely requiring page scripting — DOM state not exposable through `read_page`/`find`, or an interaction those tools cannot express — not a first resort for reading or enumerating content already available read-only. This changes text only, exactly like the existing `LIVE_EXTRACTION_NOTE`/`CONTEXT_FIRST_REPLACEMENT` precedent: no permission, classification, or executor behavior changes, and the legacy MCP-facing `host/tool-definitions.js` registry stays byte-for-byte unchanged (only the SDK-facing derived text changes, per this module's existing contract).

**9d. The coarse javascript_tool classifier — the hard limit, and the sound choice.** There is no reliable static way to determine whether arbitrary JavaScript mutates a page: `eval`, `Function()`, string-built property access and dynamic dispatch defeat source inspection, and a model's stated intent for a script is not authorization. This is not a gap to close by inspecting the script harder; any design that claims to "analyse the script and decide" is unsound, and this evidence's own second call proves why — a classifier good enough to wave through `querySelectorAll('a')...` could just as easily be fooled into waving through a navigation built from string concatenation instead of a literal `window.location.href=` assignment.

Three options were on the table:

- **Keep `javascript_tool` gated exactly as today, and rely on 9b/9c so it is rarely needed.** `isMutatingCall("javascript_tool", ...)` stays unconditionally `true`; `enforceBorrowedTabScope()` stays unchanged. A read-only script against a borrowed tab still gets rejected — accepted as a disclosed limitation, because the model should reach for `read_page`/`find` first now that 9c points it there, and should rarely need `javascript_tool` for a reading task at all.
- **Route it through the section 8 approval card, accepting the prompt cost.** Rejected: section 8's card exists only for send/submit-class actions — "Approval prompts are for send/submit-class actions only. Reading must stay automatic" is the accepted product decision this design does not re-litigate. Prompting for a `javascript_tool` call that might be read-only would prompt for ordinary reading, exactly the interaction this decision forbids widening into. Distinguishing "prompt-worthy" scripts from "silent" ones by content would need the same unsound inspection just to decide who gets asked — no more sound than deciding automatically.
- **"Inspect the script and decide."** Explicitly rejected as the general classifier, for the reason stated above. (Section 8's own narrow, disclosed `.submit()`/submit-event best-effort check for the *send/submit* gate is not a precedent for this: that check only ever adds an extra prompt on a false positive, never removes a safeguard on a false negative — the opposite direction of risk from using content inspection to lift the borrowed-tab-mutation block.)

**Choice: the first — keep scripting gated, rely on 9b/9c.** This also corrects a latent, more serious problem in task 9.3 (below), which predates this evidence: `authorizeBorrowedTabMutation(run, tabId)` (`mapping.js:190-193`) is a per-run, **per-tab** flag — `isBorrowedTabMutationAuthorized()` has no concept of which tool asked. Task 9.3, as originally written, listed "in-scope scripts" among the actions automatically authorized once a run's bound tab is legitimately in scope for interaction. Because the flag is tab-scoped, granting it for an unrelated reason — e.g. the model typing into a field on the same bound tab — would have silently also authorized every later `javascript_tool` call against that tab, **including** a navigating one: the exact call this evidence proves must stay blocked. That is the identical unsound generalization decision 9d rejects above, arrived at by a different route (a scope bug, not a content-inspection idea) but with the identical failure mode. Task 9.3 is corrected (task list below) to exclude `javascript_tool` from the automatically-authorized set: only `computer`'s non-submit-classified actions and `form_input` — both reliably classifiable per call, unlike a script — are covered by the automatic tab-level authorization. `javascript_tool` against a borrowed tab keeps requiring its own authorization, which nothing in this change grants automatically; a future change could add one deliberately, but none is proposed here, and the residual limitation (a legitimately read-only script against a borrowed tab still fails) is accepted, mitigated by 9b/9c.

This preserves, unweakened, the one thing this evidence proves is already working: the `window.location.href` rejection stays correct after 9b, 9c and the 9.3 correction land, under every future run — not only in the case captured in this evidence.

## Risks / Trade-offs

- [SDK tool/image interoperability varies by version or gateway] -> mandatory actual-image and structured-tool acceptance tests before changing the default.
- [Imported skills can request unsupported or unsafe capabilities] -> reviewed snapshots, explicit catalog, no implicit shell access, handler authorization and adversarial tests.
- [Single browser bridge is shared] -> one lease across SDK and legacy clients, explicit profile identity, no ambiguous routing.
- [MV3/native-host restart interrupts sessions] -> persisted transcript/event cursor, supervised children, bounded reconnect, no mutation replay. Stop/exit are not undo.
- [Custom gateways lag SDK protocol changes] -> version pinning and end-to-end capability tests; manual model catalog does not promise support for non-Claude models.
- [New keyed identity loses direct access to old extension storage] -> one-time export/import and key re-entry, preserve host recordings.
- [Broader Chromium compatibility varies] -> feature detection and documented tested matrix; no universal compatibility promise.
- [A fallback extraction container can look complete by length alone] -> coverage-ratio-based partial reporting (decision 9a), never solely a truncation check; live-evidence regression fixture required.
- [javascript_tool cannot be soundly split into read-only vs. mutating by content] -> keep it gated wholesale against borrowed tabs; rely on tool-description steering and read-only enumeration tools instead (decision 9d); explicitly no content-based classification, and no automatic tab-level grant extends to it (task 9.3 correction).

## Migration Plan

1. Keep this change in planning state. All implementation task checkboxes remain unchecked.
2. On a later implementation request, prove the SDK internal-tool and automatic-startup integration before adding product dependencies or changing default entry points. Capture runtime version and test evidence.
3. Establish stable extension packaging and installers, then implement the companion, settings, panel, skills, and recorder/sandbox integration. Preserve external MCP entry points as a supported interface throughout and after transition.
4. Verify all capability scenarios and browser/OS matrix. Compare representative behavior to the current executor; fail release on missing registry coverage or uncertain image delivery.
5. Make sidepanel plus SDK the documented default only after gates pass. External MCP registrations stay user-managed and supported. Rollback selects the legacy entry point and restores product registration backup; do not erase conversations or recordings.
